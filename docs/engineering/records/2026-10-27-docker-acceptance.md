# 账号改造的 Docker 验收记录

日期：2026-10-27。以下均为本轮隔离环境的实测结果，不代表现用数据库或真实模型供应商已经通过验收。

## 镜像与启动

实际执行多阶段构建：Node 22.23.4 使用 `npm ci` 后运行 TypeScript / Vite 构建；Python 3.12.16 使用 uv 0.11.8、现有 `uv.lock` 和 `--frozen --no-dev` 安装 64 个依赖。构建中没有重新解析或修改依赖版本。Node、Python、uv 和 PostgreSQL 基础镜像均固定摘要。

容器使用 UID `10001`，代码目录只读，`/tmp` 为临时文件系统。实测镜像没有开发机 `.env` 或 `.git`；匿名 API 请求返回 401，`/healthz` 与 React 页面可在未配置模型时打开。`docker compose config --quiet` 验证配置，不把展开后的密码打印到输出。

初版隔离项目 `chefmate-next-iteration` 在端口 18867 验证了显式管理员初始化、账号注册、欢迎配置、对话归属、模型设置权限、计价保存、开发者授权、停用后会话失效。两个账号互读与改写对话均返回 404。重启后账号、欢迎资料、对话标题及计价版本保留。该阶段使用本地 SQLite，仅作为账号边界的初次容器验收；最终日常部署采用 PostgreSQL 应用库。

可信代理行为也在真实 Uvicorn 中检查：来自主机的非可信 `X-Forwarded-Proto: https` 不能绕过协议核对，返回 403；容器回环地址在显式可信名单内，相同主机与 HTTPS Origin 的登录请求可成功。没有对外公开测试端口。

## 独立基础菜谱库

项目 `chefmate-next-catalog18-iteration` 使用端口 18868 和独立卷。PostgreSQL 18 健康后运行 `chefmate-storage migrate`，结构版本为 1，然后启动 App。第一次实测发现 Storage 明确要求 PostgreSQL 18+，最终 Compose 已修正版本和 `/var/lib/postgresql` 卷挂载；初次 PostgreSQL 17 测试容器已停止，未删除其卷。

空库的实际状态为 `recipe_count=0`、`data_version=null`，没有导入或伪造菜谱。随后使用仓库 [Storage 测试生成器](../../../packages/chefmate-storage/tests/conftest.py) 构造两个明确标注的合成测试菜谱，通过只读挂载的临时迁移容器先校验、再显式导入。它们只用于关系存储与 HTTP 验收，营养字段不是本轮真实食物测量。

## PostgreSQL 应用库

最终默认 Compose 包含独立 `app-db` 服务，用于账号、登录会话、用量和个人业务数据；基础菜谱库由另一 PostgreSQL 服务保存，并在首次启动自动初始化。项目 `chefmate-next-appdb-iteration` 在端口 18869 完成了真实 PostgreSQL 18 / HTTP 验收，数据库测试端口只绑定主机回环，未修改日常数据库。

通过界面对应的 API 新建两个普通账号，完成欢迎配置；第一个账号新建并改名对话、保存记忆、将主题改为深色，并上传一张 64×48 的合成图片。第二个账号读取其对话和图片均为 404，记忆和偏好保持独立。为测试图片能力，管理员保存了指向 `example.invalid` 的占位模型配置，没有调用外部供应商。

实际 SQL 查询确认 `chefmate_accounts.accounts` 当时为 3 条（管理员和两个测试用户），第一个用户的独立 schema 中 `sessions=1`、`personal_memory=1`。App 运行目录递归检查没有生成任何 `*.db` 文件，因此这次通过不是悄悄落回 SQLite 的结果。

## 成组备份与新环境恢复

真实运行 [`scripts/backup-docker.ps1`](../../../scripts/backup-docker.ps1)，停止测试 App 后用 PostgreSQL 18 的 `pg_dump -Fc -f` 导出应用库，再复制整个运行文件目录。脚本成功取得 `app.dump`（本次为 96,413 字节）与图片/设置文件，最后写入完成标记并恢复原 App。原实例重新登录后，对话、记忆、主题及图片 SHA256 均保持一致。

另建项目 `chefmate-next-appdb-restore`、全新数据库卷和运行文件卷，在空目标库执行 `pg_restore --no-owner --exit-on-error`，恢复运行文件并设置 UID/GID 为 `10001:10001`，然后启动端口 18870 的 App。验收再次确认：

- 两个账号可使用原密码登录，账号 ID 与来源实例一致。
- 欢迎资料、对话标题、用户记忆和深色主题保留。
- 图片可通过原会话与图片 ID 读取，下载内容 SHA256 与备份前完全相同。
- 第二个账号仍不能读取第一个账号的图片。
- 新恢复环境也没有生成 SQLite `*.db` 文件。

这个过程验证了应用 PostgreSQL 与运行文件的成组恢复。它不等同于对生产数据的备份认证，也没有验证跨主版本 PostgreSQL 升级或真实供应商计费。

## 固定基础数据的自动初始化

默认 Compose 已改为双库与安全初始化链，附加 catalog 文件保留兼容；默认备份也包含双库与运行文件。新增 8 项初始化检查全部通过，数据库用例连接真实 PostgreSQL，覆盖同版本重复启动、并发首次导入、不同版本保护、无身份已有行保护、同版本内容篡改拒绝、固定 358 条数据及完成标记失效。此前 17 项 seed/既有存储组合检查也通过。

358 条实际数据在随机隔离 schema 中首次导入后，再次校验全部 11 张类型化投影表，导入时间保持不变；数据库 ready 标志仍为 0 条，源文件的 2 条已审核与 356 条待审核保持原值。源码包摘要损坏在访问数据库前拒绝；已有其他数据集时完成标记撤销、旧数据不替换。上述为真实 PostgreSQL 源码验证，最终镜像启动和迁入旧个人数据的 HTTP 验收另行补记。

## 最终主实例、数据库恢复与双库备份

最终主实例使用独立项目 `chefmate-next-main-iteration`、HTTP 18875；原日常服务、原 SQLite 文件与此前测试卷均保留。镜像固定为 `chefmate-next:main-25544fa`，实际镜像 ID 为 `sha256:2d732514a3433594dbf092b14968f180f44e1e109cc72c11ad8899c5f183ff7b`，OCI revision 与构建提交为 `25544fa64e6b84a7fb0b795b02e5df51d1b6f72c`。最后仅验收文档有修改，显式使用经过核对的该源码 SHA 构建；文档不在镜像上下文中。

最后的钱包余额刷新与开发权限界面修复完成后再次构建；最终 HTTP 页面资源 `index-Bo3M3-GM.js` 与本地构建字节一致（SHA256 `0e664c21c9efbfd55cb040a2f6be6eeff4914326771c52d8e113c21aca309bf6`）。`/api/status` 报告基础库连接可用、`recipe_count=358`、数据版本 `chefmate-bundled-20261005`。SQL 中严格 ready 菜谱仍为 0；重复启动和替换最终镜像均返回 seed `verified`，没有改变原导入时间。App 使用 UID 10001，运行目录未生成 SQLite `*.db` 文件。

已迁入旧个人数据的主实例完成两次完整只读 HTTP 核对：47 个会话、329 条消息、4 张图片 SHA256、记忆正文/开关/来源、个人主题、2 条个人菜谱和 5 条饮食日志均保持一致。厨房状态首次投影可推进记忆版本与更新时间，比较以正文、开关和来源一致为准，不冒称元数据时间从不变化。已有数据的管理员作为迁入用户跳过新用户引导，资料保持空对象、AI 档案功能关闭；这一操作保留审计。对应迁移详情见[旧个人数据迁入记录](2026-10-27-daily-postgresql-migration.md)。

在没有模型请求运行时，仅停止该主实例的 `app-db`。匿名和带 Cookie 的 `/healthz`、登录状态与个人会话接口均在约 1.27–1.38 秒内返回不含 DSN、密码或堆栈的 503；带 Cookie 的静态 HTML 与 JS 保持 200。只恢复 PostgreSQL 后，原 Cookie、完整会话对象及图片 SHA256 恢复，App 启动时间未改变，证明无需重启 App 即可重新连接。

随后真实运行默认备份脚本，取得 `app.dump`、`catalog.dump` 与 6 个运行文件；8 项 SHA256/长度清单全部通过。另建项目 `chefmate-next-main-restore`、全新双库和文件卷，在空库恢复双份导出，文件恢复 UID/GID 10001 后启动 HTTP 18876。基础库初始化核对通过；66 个只读 HTTP 请求再次核实全部 47 会话、329 消息、4 图摘要与个人记录，基础库 358 条、运行目录无 SQLite。没有发送模型请求；完成后停止恢复容器，保留恢复卷及备份，主实例不受影响。

主实例后续模型验收仅使用新建合成用户，不向迁入的真实旧会话发送模型；供应商和金额核对结果单独记录。日常启动使用本机忽略目录中的同项目启动脚本，默认复用固定镜像，避免另起不同项目的空卷。GitHub 新克隆的默认启动仍是端口 18765、新建账号与 358 条基础菜谱，不包含个人历史或本机凭据。

最后补充外部连接的备份保护：脚本读取实际容器配置后立即丢弃未使用的环境信息，明确拒绝显式 DSN 或非默认主机/数据库名/用户/端口，防止只备份未使用的内置库。独立 Docker stub 回归覆盖应用/菜谱显式 DSN、外部应用主机、自定义端口与数据库名，均在停止和创建目录前拒绝，错误不包含模拟密钥；默认连接可进入后续就绪检查。另对真实主容器执行只读连接类型检查，在就绪检查处注入失败，确认默认连接识别正确，未停止 App 或创建文件。此修复仅改运维脚本与文档，不改变最终镜像源码或重启主实例。

补充 Windows 内置 PowerShell 5.1 实测：原先无 BOM 的中文源码会出现解析错误，改为 UTF-8 BOM 后 5 个运维/回归脚本均可解析；7 个备份连接保护用例在 5.1 与 7 中分别通过。5.1 实际运行完整备份校验器，对最后一次包含金额账本的双库与 6 个运行文件核对 8 项 SHA256/长度全部通过，未停止主实例。这一编码修复仅涉及主机运维脚本与说明，不修改应用逻辑。

最后一次可靠性复核发现，旧用户工作区的同步创建与记忆同步可能阻塞事件循环，导致并行认证等待超时。最终 `25544fa` 将这两个同步调用移到工作线程，仍由原工作区锁保护；24 项冷初始化、tenancy、记忆与额度专项通过。此前完整 Python/PostgreSQL 基线是 940 项通过、1 项 Windows 符号链接跳过；最终补丁的验证范围为上述 24 项专项，前端完整结果为 335 项通过。最终镜像健康后未由部署检查提前访问管理员私有工作区，保留第一次真实冷请求供并发验收。

持续负载结束并完成 72 用户重启持久性复验后，仅停止旧预览与负载项目的 5 个辅助容器，所有卷保留；主实例 18875 与原日常服务保留运行。资源采样进程已自然结束，原始数据与明确时间窗口的汇总保留在本机忽略目录，持续负载详情见[多用户负载记录](2026-10-27-multiuser-soak.md)。
