# 会员与金额额度

ChefMate 使用人民币金额控制模型请求。金额在数据库与 API 中统一保存为整数微元：`1 元 = 1,000,000 微元`。Token 用于记录模型用量与计算成本，不作为用户额度上限。

## 额度来源与扣减顺序

1. 有效的限时会员额度，同时满足周额度与 5 小时额度；有多份会员时，先用最早到期的。
2. 永久的新用户基础额度，默认 5 元；注册策略可调整后续新用户的基础金额。
3. 管理员追加的永久充值额度，按创建顺序扣减。

一轮请求可以跨来源分摊。例如用户拥有基础 5 元、30 天会员（每周 10 元、每 5 小时 2 元）、额外充值 10 元，在会员当前窗口还有 2 元的情况下，一轮 3 元费用会使用会员 2 元与基础额度 1 元。

会员额度在每个窗口内是使用上限，不会转入永久余额。会员到期不会清空基础与充值额度，也不会改变此前已发起请求的归属。

## 有效期与首次使用窗口

- 会员有效期从管理员开通时开始，到 `expires_at` 结束。
- 会员第一次参与正金额预留时，启动一周与 5 小时窗口；只读取额度或零金额请求不会启动窗口。
- 窗口使用固定起止时间，不按自然周计算，也不使用最近 7 天的滚动求和。窗口结束后，下一次参与正金额预留时才启动新的窗口。
- 5 小时窗口同时受所在周限制，结束时间不超过周窗口结束与会员到期时间。
- 后面尚未参与分摊的会员不会被提前启动。已成功预留后，即使请求取消，窗口起点也会保留。

例如第一次会员预留发生在周三 09:00，周窗口截至下周三 09:00，第一个 5 小时窗口截至当日 14:00。如果当天 16:00 再次使用，新的 5 小时窗口从 16:00 开始。周额度用完后，即使 5 小时窗口还有余额，也会继续使用永久额度。

## 预留、结算与管理员核对

发起模型调用前，系统根据不可变的模型价格快照和请求上限预留金额。每轮模型调用独立记录分摊来源与窗口；并发请求在同一数据库事务中核对额度，避免重复占用同一份余额。

模型返回用量后，系统按实际成本缩减预留；未报告的用量保留为独立标记的预估占用。进程重启或请求超时不会直接抹掉可能已经发生的费用，恢复流程会保留这些预估，供管理员核对。

核对记录不会修改原始 Token、原始价格或原始报告金额。退款沿原来的来源与窗口返还：旧 5 小时窗口的退款不会增加新的 5 小时窗口。原窗口后来已经被其他请求占用时，再次上调核对金额也不会挤占其他请求已经使用的额度；无法放回原窗口的真实费用计入永久额度的超支。新增永久额度会参与抵扣这些超支。

实际费用超出预留时，系统仍会记录已发生费用。额度不足会阻止后续调用；不会为了使余额好看而丢弃费用。

## 管理员操作与 API

管理平台的“用户与额度 → 额度”显示来源、窗口、已用金额、预留与剩余金额；用户“我的额度”和账号小卡片以百分比显示使用状态。两种界面使用同一份额度记录。管理员可追加永久充值、开通会员与填写原因撤销会员。撤销会停止新请求使用该会员，历史记录和已经发起的预留会保留。

| 接口 | 用途 |
| --- | --- |
| `GET /api/auth/entitlements` | 当前用户的资金来源与额度窗口 |
| `GET /api/admin/users/{id}/entitlements` | 管理员查看指定用户 |
| `POST /api/admin/users/{id}/credit-grants` | 追加永久充值 |
| `POST /api/admin/users/{id}/memberships` | 开通会员 |
| `POST /api/admin/users/{id}/memberships/{membership_id}/revoke` | 按版本撤销会员 |

充值请求示例：

```json
{"amount_micros":10000000,"label":"额外充值额度","request_id":"unique-operation-id"}
```

会员请求示例：

```json
{"label":"ChefMate 会员","duration_days":30,"weekly_limit_micros":10000000,"five_hour_limit_micros":2000000,"request_id":"another-unique-operation-id"}
```

充值与会员请求必须带 `request_id`。重试相同操作使用原来的标识与原来的内容；内容不一致会返回冲突，避免网络重试重复增加额度。撤销请求提交当前 `revision` 与 `reason`，状态已经改变时返回冲突，要求重新读取后复核。

上述接口均返回 `{ "user": ..., "entitlements": ... }`。用户对象的 `quota.funds` 与 `entitlements` 使用相同结构：

- `available_micros`：已经扣除预留、并考虑永久超支的当前总可用金额；`null` 表示不限额。
- `permanent`：永久总额、已用、预留、剩余、超支与各个基础/充值来源。
- `memberships`：有效期、状态、终止版本与原因，以及 `week`、`five_hour` 窗口。
- `used_micros` 已包含其中的 `estimated_micros`，二者不能再次相加。`reserved_micros` 另外列出。
- 未开始窗口的 `starts_at`、`resets_at` 为 `null`；读取这些状态不会写入窗口。

## 保存与套用会员模板

在管理员额度面板选择“开通限时会员”后，可以选择已保存的会员模板并点击“套用模板”。套用会填入这次的会员名称、有效期、每周金额和每 5 小时金额，管理员仍可继续调整。只有点击“确认开通会员”才会授予；选择模板、保存模板和编辑模板均不会直接授予会员。

“管理模板”支持新增、编辑与删除多个常用方案。模板名称用于区分方案；开通后的会员名称单独保存。修改或删除模板不会追改已经发放的会员，也不会改变本次已经填入的开通参数。

| 接口 | 用途 |
| --- | --- |
| `GET /api/admin/membership-templates` | 读取模板列表与版本 |
| `POST /api/admin/membership-templates` | 新增模板 |
| `PATCH /api/admin/membership-templates/{id}` | 编辑模板 |
| `DELETE /api/admin/membership-templates/{id}?revision=N` | 删除模板 |

这些接口仅对管理员开放，并执行同源校验。模板保存在 `account_settings` 的 `membership_templates` JSON 中，返回 `{ "revision": 1, "items": [...] }`。空列表读取不会写库或自动创建方案。

新增请求携带当前 `revision` 与 `name`、`label`、`duration_days`、`weekly_limit_micros`、`five_hour_limit_micros`；编辑请求使用 `{ "revision": N, "values": {...} }`。修改使用列表级版本校验，另一位管理员已经修改列表时返回 `409`。界面保留草稿，读取最新版本后显示当前方案，管理员复核并再次保存；不会自动覆盖其他人的修改。网络响应丢失时，可读取最新版本确认上次保存结果，避免重复创建。

## 升级已有账号与数据库迁移

已有账号保留原基础总金额、已发生费用、未核对预估与未完成预留。初始化分摊账本时，历史金额映射回原基础来源，不补发一份新的 5 元；原不限额账号继续不限额。默认 5 元只用于按当前注册策略创建的新账号。

在线 PostgreSQL 迁移需要连同以下财务表一起复制：`account_credit_grants`、`account_memberships`、`account_membership_windows`、`account_budget_turns`、`account_budget_portions`、`account_budget_allocations`，以及原有用量、预留与核对表。旧版本没有这些新表时，复制完成后执行账本的已有账号迁移，保留原来的已用与预留。不要只复制账号总额、遗漏分摊历史。

当前功能提供管理员记账与会员授予；不包含支付渠道、在线收款或自动续费。
